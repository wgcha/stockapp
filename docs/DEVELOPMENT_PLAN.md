# 개발 현황 및 단계별 계획

기준일: 2026-10-08. 최신 사용자 요청이 기존 실거래 개발 계획보다 우선한다.

## 제품 범위

**프로그램은 가이드만 제공하며 실거래를 실행하지 않는다.** 사용자는 Telegram에서
투자조건·보유·관심종목을 등록하고 질문하거나 정기 가이드를 받는다. 실제 매매는
사용자가 증권사 앱에서 직접 한다. 변경된 보유정보는 봇에도 반영해야 한다.

포함: 개인화 문답, 시황·종목 가이드, 근거·출처·신선도·자료 부족 표시, 자동 가이드,
접근 통제, 상시 서버 운영, 내부 모의평가·전략 검증.
제외: 실주문 전송·취소·정정·체결 대사 및 미래에셋 실거래 어댑터 개발.
기존 승인형 모의주문은 내부 검증용으로 유지하며 일반 사용자 문답에서는 생성하지 않는다.
내부 코드의 생성자 옵션을 명시한 경우만 연구 경로를 사용한다. 환경변수나 사용자 명령으로
옵션을 켜지 않는다. 과거 실거래 활성화 플래그로 실제 주문을 재활성화할 수 없게 차단한다.

## 진행 규칙

개발은 단계별로 진행한다. 각 단계 완료 시 변경 내용, 검증 결과, 제한, 다음 단계 범위를
요약해 사용자에게 보고하고 **명시적인 승인을 받은 뒤 다음 단계에 착수한다.**
사용자 승인으로 3단계까지 로컬 구현·검증을 완료했다. 2026-09-12 승인으로 4단계를 진행한다.
2026-10-07 사용자 승인으로 5단계 로컬 개발을 진행한다. 4단계 운영 인수는 운영 대상과
비밀 설정 대기로 유지하며 실제 연결·배포 완료로 표시하지 않는다.

### 5단계 승인된 구현 범위

2026-10-08 계속 개발 요청으로 아래 후속 개선을 완료했다. 기존 가이드 전용 범위와
실제 운영·실증 대기 상태를 유지한다.

- 인증정보 없이 기존 DB에서 특정 전략·버전 보고를 조회하는 로컬 CLI를 추가한다.
  `python -m stock_guide_agent.cli --strategy-report time_series_momentum 1.0.0 --data-dir <기존 데이터 디렉터리>`.
  `--env-file`과 `KRX_CALENDAR_OVERRIDES`는 기존 설정 해석을 따른다. 기존 `strategies.sqlite3`와
  정확한 전략 ID·버전이 필요하고, 읽기 전용으로 열어 DB 생성·마이그레이션·런타임 기동·API 접속
  없이 조회한다. 필수 DB/레코드 실패는 고정 오류와 exit 1, 원장 누락·오류·달력 불확실성은
  0일과 구분해 확인 불가로 표시한다. 저장 스냅샷과 현재 `/30` 진행을 같이 보여주며,
  멀티 DB 조회는 원자적이지 않아 안정된 시점이 필요하면 봇을 멈추거나 백업 복사본을 사용한다.
- 백테스트 가격·비용 입력의 비정상 수치를 계산 전에 거부하고 기존 정상 결과를 확인한다.
- 정상 모의일수는 같은 전략·버전·사용자·거래일의 평가와 자산 평가를 연결한다.
  단타는 같은 날짜의 모든 종목이 정상인 경우만 인정한다. 검증일 이후와 휴장일은
  승인 판단에서 제외하며 거래 달력을 확인할 수 없으면 검증을 보류한다.
- NaN·무한값·잘못된 범위와 자료형을 포함한 검증 보고서는 승인 기준을 통과하지 못한다.
  정상 모의일수 집계의 금융 지표는 SQLite `typeof`가 integer/real인 값만 인정해 TEXT/BLOB 강제 변환을 막는다.
- 소유자용 전략별 보고에 검증 시점·성과·비용 가정·근거·정상일수·미충족 요건을 표시한다.
  미검증 상태와 기술 검증 완료, 소유자 활성화를 구분한다.
- 연결된 해당 모의원장이 있는 신규 전략 활성화는 현재 정상 모의일수 30일과 사용 가능한
  거래일 달력을 요구한다. 기존에 승인된 전략은 현재 일수 재계산만으로 자동 취소하지 않으며,
  숫자 검증에 실패한 과거 보고서는 다시 읽을 때 승인 상태를 중지로 낮춘다.
- 가이드·내부 연구의 중단 스위치는 `users.sqlite3`의 `execution_safety_state`에서 재시작 후
  복원한다. 저장 실패 시 메모리상 중단은 유지되고 고정 오류를 반환한다. 외부 주문 기능은 추가하지 않는다.
- 관련 회귀와 전체 테스트를 수행했고 Sol이 독립 검수했다. 실제 증거 누적과 전략 활성화는
  로컬 구현 완료와 구분하며 정상 모의일수·분봉 요건을 충족한 것처럼 표시하지 않는다.
- 2026-10-08 전체 unittest는 337개 중 336개 통과, Windows 심볼릭 링크 권한 문제로 1개 skip이다.
  Astra가 SQL 근거 집계와 손상 DB 사례를 독립 재검수했다. WAL 최신 보고 날짜와 근거 수 표시를
  확인했고 로컬 보고 테스트 12개가 통과했다. 가이드 전용 범위와 4단계
  운영 인수 대기, 정상 모의일수 30일 및 장중 378 세션 조건은 그대로 유지한다.

## 코드에서 확인한 개선 근거

- 2단계에서 runtime.py의 폴링·알림 실패 격리, SQLite 처리 상태·offset 복원과 별도 답변
  재시도를 구현했다. 중단 요청 자동 재실행은 하지 않으며 답변 중복·유실 가능성과 단일
  인스턴스 전제는 [메시지 복구·보안 문서](MESSAGE_RECOVERY_SECURITY.md)에 명시했다.
- 3단계에서 service.py와 scheduled_handlers.py에 공통 XKRX 달력을 적용했다.
  최신 임시휴장·특수 장시간 공지는 운영자가 확인하고 로컬 보정 파일에 반영한다.
- scheduler.py는 3회 실패 후 회로를 열고 냉각 후 회복을 탐색한다. 작업 상태 조회와
  봇 중지 상태의 복구 CLI를 제공한다. 재시작 시 중단 작업을 실패로 전환한다.
- 정기 작업을 단일 백그라운드 작업자로 분리하고 중복 실행을 막았다. 시간 초과는
  상태로 표시하며 강제 종료하지 않는다. 종료가 지연되는 제한은 운영 문서에 명시했다.
- 같은 데이터 경로의 중복 기동·백업을 OS 잠금으로 차단하고, 오프라인 SQLite 백업과
  새 경로 복원을 검증했다. 실제 운영 DB·서버 검증은 4단계다.
- doctor/runtime 설정 검증을 공유하고 유한값·범위를 검사한다. doctor 성공을
  실제 연결·백업 복원 성공으로 간주하지 않는다.
- ExecutionState는 kill switch의 활성 여부와 사유만 `users.sqlite3`의
  `execution_safety_state`에 저장한다. 시작 시 값이 없으면 꺼진 상태로 시작하고, 저장값이
  손상됐거나 DB를 읽지 못하면 런타임 시작을 거부한다. 중단 해제는 DB에 먼저 저장한 뒤
  메모리 상태를 지운다. 저장 실패 시 메모리 중단은 계속 유지되고 고정 오류를 반환하지만,
  프로세스 종료 뒤 저장되지 않은 변경을 복원할 수는 없다. 이 변경 이전에 메모리에만 있던
  중단 상태도 복구할 수 없다. API 상태·일일 손익·주문 제안 등 transient ExecutionState는
  재시작 후 복원하지 않는다. 실주문 상태 원장·체결 대사는 현재 범위에서 개발하지 않는다.
- 보유정보는 수동 입력과 실제 계좌를 구분하고 갱신 시각을 명확히 한다.

## 구조와 작업 방식

GPT-6.1 Sol이 문제 정의·범위 설정·코드 탐색·통합·최종 검수를 맡고, 구현은 기본적으로
GPT-6 Luna 추론 강도 High/XHigh 에이전트에 맡긴다. 명확히 독립적인 작업만 병렬화하며,
에이전트 수를 최소화하고 같은 코드 탐색을 반복하지 않는다.
사용자 명령 / 가이드 / 자료 수집 / 전략 연구 / 운영·복구 경계를 두며 큰 서비스 파일은
수정하는 기능부터 분리한다. 같은 파일의 동시 수정을 피한다.
달력·재시도·설정 검증은 유지보수되는 패키지를 먼저 검토하고 지원 범위·라이선스·버전을 확인한다.
관련 계획 항목·함수·테스트부터 필요한 부분만 읽고, 큰 변경 전 계획을 갱신한다.
상태는 예정·진행·구현완료·검증완료·운영확인으로 구분하고 변경 파일·검증 결과를 기록한다.
