# 2단계: 메시지 복구와 보안 운영 기준

2026-09-10. 이번 단계는 로컬 구현·장애 주입 테스트다. 실제 Telegram 연결, 서버 권한 적용,
백업 복원과 연속 운영 검증을 완료한 것으로 간주하지 않는다.

후속 3단계에서 데이터 경로의 OS 잠금과 로컬 백업·복원 검증을 추가했다.
최신 명령·제한은 [운영 문서](OPERATIONS.md)를 따른다. 아래는 2단계 당시의 기록이다.

## 처리 구조와 보장 범위

`runtime.py`는 Telegram 수신을 조정하고, `messaging.py`는 표준 라이브러리 SQLite로
업데이트 처리 상태와 발송 대기열을 관리한다. `telegram.py`는 개인 채팅과 발송 권한을
검사한다. 네트워크 호출을 DB 트랜잭션 안에 두지 않는다. 새 외부 패키지는 필요하지 않았다.

1. 업데이트 ID를 정렬·검사한 뒤 SQLite에 `processing`과 다음 offset을 원자적으로 저장한다.
2. 그 저장이 성공한 요청만 서비스가 처리한다. 저장 실패 시 다음 요청으로 건너뛰지 않는다.
3. 성공은 `completed`, 실패는 `failed`로 기록한다. 이 처리 원장에는 실패 원문·수신 메시지
   본문을 저장하지 않는다. 사용자 설정 DB에는 기존처럼 입력한 투자조건 등 필요한 정보가 남는다.
4. 재시작 시 `processing`은 `interrupted`로 표시하고 소유자에게 ID와 재확인 안내를 보낸다.
   이미 주장한 ID는 다시 실행하지 않는다. 처리 전에 중단돼 실제 효과가 없을 수도 있고,
   저장 후 중단돼 효과가 이미 반영됐을 수도 있다. 사용자는 `내 설정`·`내 보유`로 확인한 뒤
   필요한 요청만 다시 보낸다. 이 구조는 요청 효과 중복 방지를 우선하며 무손실·정확히 한 번
   실행을 보장하지 않는다. 복구 알림 자체도 장애·대기열 포화로 전달되지 않을 수 있다.
5. 답변은 먼저 outbox에 기록하며 서비스 요청을 재실행하지 않고 전송만 재시도한다.
   최초 전송을 포함해 5번까지 시도하고 실패 간격은 5·10·20·40초다. 5번째 실패 또는
   24시간 만료 시 본문을 제거한다. 재시도 간격은 최소 대기이며 폴링·정기 작업에 따라 늦어질 수 있다.
6. 전송 성공 후 DB 기록 실패 또는 Telegram 응답 유실 시 같은 답변이 다시 도착할 수 있다.
   장시간 장애 중의 답변은 재시도 한도에 따라 소실될 수 있으므로 복구 후 재질문한다.
7. Telegram 폴링 오류는 1초부터 최대 60초까지 백오프하며 CLI는 즉시 반환되는 실패 루프에
   1초 대기를 둔다. 답변 재시도와 정기 작업 예외는 폴링 실패와 분리한다.

자동 가이드의 마지막 발송일은 durable 모드에서 **발송 대기열 등록일**이다. 실제 도착을
보증하는 영수증이 아니다. 전송이 끝내 실패하면 사용자가 `오늘 가이드`로 다시 요청한다.

Telegram은 수신 업데이트를 24시간 이상 보관하지 않으며, 일주일 이상 새 업데이트가 없으면
다음 ID를 임의로 정할 수 있다. 마지막 claim 후 7일 이상이고 처리 중인 행이 없으면 오래된
수신 기록과 offset을 초기화해 더 낮은 새 ID를 받을 수 있게 한다.
[공식 수신·업데이트 명세](https://core.telegram.org/bots/api#getting-updates),
[공식 offset 명세](https://core.telegram.org/bots/api#getupdates).

## 운영 전제와 데이터

- **봇 하나당 데이터 디렉터리 하나, 실행 프로세스·컨테이너 하나**를 사용한다. 노트북과
  서버에서 같은 봇을 동시에 실행하거나 여러 replica로 늘리지 않는다. outbox는 다중 작업자
  lease를 구현하지 않았다. 수신 ID claim만 원자적이라고 전체 다중 프로세스 운영이 안전한 것은 아니다.
- `AGENT_DATA_DIR/messages.sqlite3`와 WAL/SHM은 개인 가이드를 일시 보유할 수 있다.
  사용자 설정·보유정보 DB와 같은 접근 통제로 취급한다. inbox에는 ID·상태·시각만 저장한다.
- pending 본문은 전체 1,000건·사용자별 100건으로 제한한다. 한도를 넘으면 새 enqueue가
  실패하며 요청의 일부 상태가 이미 저장됐을 수도 있다. 해당 요청을 자동 재실행하지 않는다.
- 전송 완료·실패 한도·만료 후 본문은 NULL로 제거하며 `secure_delete`를 적용한다.
  WAL·백업·디스크 잔존 데이터의 완전 삭제나 저장 시 암호화를 보장하지 않는다.
- 발신 ID·chat ID·상태·시각과 활동 중 수신 ID 기록은 유지된다. 감사 메타데이터 장기 정리 정책은
  운영 관측과 함께 후속 검토한다. 출력에서 숨기는 것과 파일 암호화는 다른 보호 조치다.
- 첫 도입은 새 DB를 자동 생성한다. 되돌릴 때 기존 messages DB를 삭제해 중복방지를
  초기화하지 않는다. 다른 봇의 DB를 재사용하지 않는다. 실제 백업·복원 검증은 3단계다.

## 권한과 로그 보호

- 수신은 허용 사용자·일반 개인 텍스트 채팅만 처리한다. chat ID와 sender ID가 같아야 하며
  그룹·봇 발신·비정상 ID는 무시한다. 허용되지 않은 요청에는 응답하지 않는다.
- `TELEGRAM_OWNER_CHAT_ID`는 생략하거나 `TELEGRAM_OWNER_USER_ID`와 같아야 한다.
  이전의 다른 소유자 알림 채팅 설정은 이제 기동·doctor에서 거부한다.
- 답변 등록·실제 전송 때 현재 허용 목록을 다시 검사한다. 재시작하며 회원을 제외하면
  그 회원에게 보내려던 답변은 전송하지 않고 본문을 제거한다.
- Telegram API 오류의 원문 설명, HTTP 실패의 URL·응답 본문, 정기 작업 예외 원문을
  진단 알림에 포함하지 않는다. 요청 repr/redacted에서 인증값·계좌 헤더·메시지 본문을 숨긴다.
  개발자가 별도로 원시 객체 속성을 출력하면 이 보호를 우회할 수 있으므로 그렇게 기록하지 않는다.

## 배포 시 적용할 접근권한·키 교체 절차

이 절차는 준비 문서다. 이번 단계에서 실제 `.env`, 서버 ACL, 백업 위치를 읽거나 변경하지 않았다.

1. 운영 서비스 계정을 정하고 소스·비밀 설정·데이터 디렉터리를 구분한다. 비밀 설정과 DB,
   백업은 서비스 계정과 필요한 관리자만 읽을 수 있는지 확인한다. Windows는 해당 경로의
   ACL, Linux는 소유자·그룹·권한을 확인한 뒤 불필요한 접근을 제거한다.
2. `.env`는 커밋하거나 채팅·로그에 붙이지 않는다. 토큰을 명령 인자나 공개 터미널 기록에
   남기지 않는다. 운영체제 저장장치 암호화와 백업 접근 통제 적용 여부를 확인한다.
3. 키 교체 시 단일 봇 프로세스를 중지하고 발급 기관에서 기존 키를 폐기·새로 발급받는다.
   로컬 비밀 설정만 교체하고 기존 메시지·사용자 DB를 보존한다. doctor 후 단일 인스턴스로
   재기동해 본인 테스트 메시지를 확인한다. 다른 봇으로 변경하는 경우에는 새 데이터 경로를 쓴다.
4. 회원 제외는 허용 목록을 수정하고 재시작해 적용한다. 소유자 Telegram 계정은 2단계 인증과
   접속 기기 점검을 사용한다. 계정 탈취 대응은 프로그램 내 사용자 ID 검사만으로 대체되지 않는다.
5. 백업 위치 권한과 복원 후 개인화·중복방지 상태가 보존되는지 실제로 확인한 뒤 운영 인수한다.

## 검증과 다음 단계

저장소 단위 테스트와 실제 서비스·SQLite를 연결한 재시작 테스트로 상태 보존, 중단 요청
미재실행, 발송 재시도, 낮은 새 update ID 수신, 수신자 변경, 오류 비밀값 비노출을 검증한다.
최종 개수·검수 결과는 CHANGELOG에 기록한다. 3단계는 사용자 승인 전 시작하지 않는다.
