## 거래일·시간 판단

- 일반 거래일은 패키지의 개장/폐장 시각을 사용한다. 종가 평가는 폐장 후 10분부터 수행한다.
- 자동 가이드 시작은 `max(설정 시각, 해당 거래일 개장+10분)`이며 그 뒤 10분이 발송창이다.
- 휴장일에는 자동 발송·장 마감 평가를 건너뛴다. 미지원 날짜·의존성·달력 오류 때는
  평일로 추정하지 않고 해당 정기 작업을 실패 처리한다.
- 패키지 데이터가 최신 거래소 공고를 자동으로 반영하는 것은 아니다. 배포 전 해당 연도의
  신규 공휴일·임시 휴장·특별 개장 공고를 검토해야 한다. 최신성 검증은 운영 인수 기준이다.

확인한 공고를 반영할 때는 로컬 JSON을 만들고 `KRX_CALENDAR_OVERRIDES`에 경로를 지정한다.
아래 날짜·URL은 형식 설명용이며 실제 거래소 공고가 아니다. 그대로 운영에 적용하지 않는다.

```json
{
  "2026-07-16": {"closed": true, "source_url": "https://example.test/verified-notice"},
  "2026-07-17": {"open": "10:00", "close": "16:30", "source_url": "https://example.test/verified-notice"}
}
```

시각은 KST이며 출처 HTTPS URL이 필수다. 앱은 URL 진위를 자동 검증하거나 다운로드하지 않는다.
허용된 운영자가 공식 공고를 확인한 뒤 기록한다. 파일 오류는 기동·doctor에서 거부한다.
파일은 재시작 때 읽으므로 변경 후 재기동한다. 임의 override를 사용자 Telegram 명령으로 받지 않는다.

## 정기 작업과 응답성

정기 수집·연구는 단일 백그라운드 worker에서 순차 실행하며 Telegram 폴링은 별도로 진행한다.
동일 batch가 실행 중이면 새 batch를 시작하지 않는다. 오래 걸린 앞 작업 뒤에는 경과 시간을
반영한 시각을 다음 작업에 전달해 지난 발송창을 현재처럼 취급하지 않는다.

3회 연속 실패하면 기본 15분 동안 회로를 열고, 이후 한 번 재시도한다. 성공하면 정상 주기로
돌아가며 실패하면 다시 대기한다. 프로세스 재시작 시 중단된 실행 marker는 실패로 기록하고
복구한다. 기본 5분을 넘긴 실행은 `execution_overdue`로 조회한다.

시간 초과는 **강제 종료가 아닌 상태 표시**다. Python thread를 강제로 끊지 않으며 기존
HTTP timeout이 개별 요청에 적용된다. 하나의 정기 작업이 영구 정지하면 다른 정기 작업도
대기하지만 일반 문답은 별도 경로로 처리된다. 사용자 요청 자체가 느린 API를 호출하는 시간,
CPU 경쟁까지 없애거나 일정 응답 시간을 보장하지는 않는다.

```powershell
python -m stock_guide_agent.cli --jobs-status --data-dir E:\work\data
# 수동 회로 초기화는 봇을 먼저 중지하고 정확한 ID로 수행
python -m stock_guide_agent.cli --reset-job strategy_validation --data-dir E:\work\data
```

상태 조회는 읽기 전용이며 API 키가 필요 없다. 초기화는 데이터 잠금을 획득한 로컬 운영자만
가능하며 잘못된 ID와 실행 중인 작업 초기화는 거부한다. 기본 소유자 Telegram 명령을 추가한
것은 아니다. 상태 DB가 없는 경우 임의의 작업 DB를 새로 만들지 않는다.

## 단일 인스턴스와 종료

CLI로 실행한 봇은 `.runtime.lock`의 OS 파일 잠금을 전체 수명 동안 유지한다. 같은 데이터
디렉터리에서 두 봇 또는 봇과 백업/초기화를 함께 실행할 수 없다. 잠금 파일은 남아 있어도
파일 존재 자체로 잠그지 않으며, OS 잠금은 프로세스 종료 시 풀린다. 파일을 수동 삭제하지 않는다.

정상 종료는 worker가 끝난 뒤 데이터 잠금을 해제한다. handler가 영구 정지하면 정상 종료도
기다릴 수 있다. 이때 실행 중인 프로세스를 운영체제에서 종료한 뒤 중단 상태를 확인해 재기동한다.
프로세스가 실제 종료됐는지 확인하기 전에 잠금이나 데이터 파일을 강제로 지우지 않는다.
라이브러리 API로 runtime을 직접 구성할 때도 호출자가 동일 잠금과 close 순서를 지켜야 한다.

## 오프라인 백업과 새 경로 복원

봇을 중지하고 먼저 대상의 **부모 폴더**를 준비한다. 백업·복원 대상 폴더 자체는 없어야 한다.

```powershell
python -m stock_guide_agent.cli --backup-to E:\work\backups\snapshot-001 --data-dir E:\work\data
python -m stock_guide_agent.cli --restore-from E:\work\backups\snapshot-001 --restore-to E:\work\restored-data
```

- 알려진 SQLite 9종 중 존재하는 파일을 SQLite backup API로 복사한다. 같은 폴더에 등록되지
  않은 `.sqlite3`가 있으면 불완전한 성공을 만들지 않고 거부한다. 새 저장소 추가 시 registry를 갱신한다.
- `.env`, 키 파일, 로그와 임의 파일은 복사하지 않는다. 달력 override 파일도 별도로 보관한다.
  개인정보가 담긴 사용자·가이드 DB는 포함되므로 백업 접근권한은 데이터 폴더와 동일하게 보호한다.
- 각 파일에 무결성 검사와 크기·SHA-256을 기록한다. 복원은 manifest allowlist·크기·해시·
  SQLite 무결성을 검증한 임시 폴더만 새 경로로 이동한다. 기존 데이터 폴더는 덮어쓰지 않는다.
- 해시는 손상 탐지용이며 신뢰되지 않은 백업 제작자의 진위를 인증하지 않는다. 신뢰하는
  백업만 사용하고 원본·백업 디렉터리를 다른 프로그램이 동시에 수정하지 않도록 한다.
- symlink/junction 경로와 원본 내부·상위 대상으로의 백업/복원은 거부한다.
- 복원 검증은 사용자 평가금·메시지 offset·이미 처리한 ID의 중복 방지를 실제 DB에서 확인했다.
  운영 전환은 복원된 새 경로를 검토한 뒤 `AGENT_DATA_DIR`를 변경해 수행한다.
  실제 운영 경로 전환은 이번 단계에서 하지 않았다.

## 설정 검증과 완료 범위

doctor와 runtime은 공통 수치 검증을 사용해 NaN·무한대·지원 범위 밖 금액/횟수/시간을 거부한다.
doctor 성공은 네트워크 연결, 최신 거래소 공고 확인 또는 실서버 접근권한 검증의 대체물이 아니다.
최종 테스트·검수 결과는 CHANGELOG에 기록하며 5단계는 사용자 승인 전 착수하지 않는다.
